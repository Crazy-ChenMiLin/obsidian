#### L 1 本地缓存 Caffeine

Key 格式：`feed:public:{size}:{page}:v1`

- 先查本机内存缓存
- 命中：直接返回数据，速度最快
- 未命中：往下走 L 2

#### L 2 Redis 片段缓存

拆成两部分存：

- 动态 ID 列表：`feed:public:ids:{size}:{hourSlot}:{page}`
- 单条动态详情：`feed:item:{id}`
- 还有 hasMore 有没有下一页标记
- 命中：组装数据直接返回
- 未命中：往下走 L 3 回源 DB




# 缓存计数 + 事件监听 + 快照更新流程 :

- 监听点赞 / 收藏事件 → 拿到**知文 ID**
- 查一下这篇知文的作者 → 更新作者的总点赞 / 收藏计数（Redis 计数）
	- 这里是真正总的数量--redis 里面
- **核心：去 Redis 查反向索引** → 找到所有包含这篇知文的 Feed 页面 key
    - 查**当前小时**的索引
    - 查**上一小时**的索引
    - 把所有 key 放进 `LinkedHashSet` 里
- 遍历这些 key，**先更新本地缓存 (Caffeine)**，**再更新 Redis 缓存**
	- 这里是 feed 流展示总的数量---- redis 里面
- 更新方式：把缓存数据转成对象 → 改数字 → 写回缓存

## 问题 2：为什么必须「直接改 feed 的数量」，而不是「去查」？

### 1. 缓存是**静态死数据**，不是动态查询

Feed 缓存存的是 **固定 JSON 字符串**，不是「实时查询语句」

它不会自己去查最新的点赞数，你不改，它永远是旧数字。

## 异步同步：设计上就禁止实时同步**！
- **不是在这段监听代码里同步**
- 而是有一个**独立的后台定时任务**（比如每 10 分钟 / 每小时执行一次）
- 后台任务批量把 Redis 的计数**一次性同步到数据库**做持久化
- 这个同步代码**在别的文件里**，你当前看的监听器**完全不负责这个**
