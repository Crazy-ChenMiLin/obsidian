## 三、为什么不用「定制化 SDS 计数」来存点赞状态？

既然 SDS 也是二进制打包，为什么不能用它来存用户的点赞状态？

核心原因是**两者的设计目标完全不同**：

1. **存储粒度不同**
    
    - SDS 计数：按「计数器组」打包，适合存储**少量大数值**（如 1 篇笔记的点赞、收藏、评论 3 个计数器）
    - Bitmap：按「位」存储，适合存储**大量小布尔值**（如 100 万用户的点赞状态）
    
2. **操作效率不同**
    
    - SDS 计数：更新单个计数器需要读取整个二进制字符串→解析→修改→重新写入，适合少量更新
    - Bitmap：更新单个位只需要执行 `SETBIT` 命令，不需要读取整个 Key，适合海量更新
    
3. **统计能力不同**
    
    - SDS 计数：只能得到预先打包好的总数，无法动态统计
    - Bitmap：可以随时统计任意范围内的点赞数（如 `BITCOUNT key 0 10000` 统计前 1 万个用户的点赞数）

# 一、Redis 点赞 Bitmap + 定制 SDS 知识重整

## 1. 点赞 Bitmap 大 Key 优化方案

采用分片思路，不使用一个超大 Bitmap 大 Key；查询时按**取模规则拆分出 10 个小 Key**，统计点赞数时，分别读取每个小 Key 对应的位值，累加求和得出总数。

## 2. Bitmap 幂等性原理

依靠 Redis 原子位操作实现点赞幂等：

- `GETBIT`：查询用户是否已点赞
- `SETBIT`：设置点赞状态
    这些是原子操作。
    位值一旦被设为 1（已点赞），重复执行`SETBIT`不会改变结果，不会产生重复计数，天然保障操作幂等。
   

## 3. 点赞场景为什么不用 Hash

- Redis 单线程下，**单个 HGET、HSET 命令是原子操作**；
- 但业务中`HGET 判断 + HSET 更新`是组合操作，中间会被其他命令插入打断，整体丧失原子性，并发下容易出现计数错乱。

## 4. 为什么不用定制化 SDS 存储点赞状态

SDS 和 Bitmap 设计目标完全不同，无法替代：

1. **存储粒度**
    
    定制 SDS：适合存**少量大数值**，用于计数器组；
    
    Bitmap：按位存储，适合存**海量布尔状态**（百万级用户点赞标记）。
2. **操作效率**
    
    定制 SDS：更新需读取全量二进制串、解析、修改、重写，开销大；
    
    Bitmap：`SETBIT`直接操作单个位，无需读取整个 Key，适配海量高并发更新。
3. **统计能力**
    
    定制 SDS：仅能获取预设好的总计数，无法灵活范围统计；
    
    Bitmap：支持`BITCOUNT`，可任意区间快速统计点赞人数。

## 5. Lua + Bitmap + SDS 配合使用

- Bitmap：记录每一位用户的点赞布尔状态；
- 定制 SDS：专门存储点赞总数等聚合数值；
- Lua 脚本：实现原子联动，点赞时通过脚本同步更新 Bitmap 状态和 SDS 计数，保证两个操作同时成功或失败。

## 6. Bitmap 数据同步到 MySQL

1. 不选用 Lua 的原因：Lua 只适合 Redis 内部原子操作，**跨 Redis 与 MySQL 的系统同步**，Lua 不适用，维护性差。
2. 落地同步方式：

- 定时任务批量将 Bitmap 点赞状态同步写入 MySQL；
- 定时执行`BITCOUNT`统计真实点赞数，和 SDS 计数做比对，数据不一致时自动重建 SDS 计数。

## 7. 技术方案适用场景汇总

| 技术方案            | 适用场景                           | 核心优势                            |
| --------------- | ------------------------------ | ------------------------------- |
| Redis 分片 Bitmap | 点赞、签到、在线状态等布尔存储；高并发幂等判重、海量数据统计 | 内存占用极低、位操作原子性、支持范围快速统计          |
