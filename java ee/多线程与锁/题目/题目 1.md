## 参考答案与解析

### 一、判断题

1. ❌ 解析：ThreadLocal 是**线程隔离**，不是解决共享变量的安全问题；共享变量的安全问题用 synchronized、Lock 解决。
2. ✅ 解析：GC 会回收弱引用的 key，但强引用的 value 会一直存在，直到线程死亡。
3. ❌ 解析：InheritableThreadLocal 只在 `new Thread ()` 创建新线程时复制数据，线程池复用线程时会拿到旧数据。
4. ✅ 解析：afterCompletion 是请求的最后一步，无论业务代码是否抛出异常，都会执行，在这里清理最安全。
5. ✅ 解析：Feign 默认是同步调用，RequestInterceptor 和业务代码在同一个线程中执行，所以能拿到 ThreadLocal 数据。

### 二、单选题

1. B 解析：ThreadLocalMap 只有散列数组，没有链表，冲突时线性向后找空位置。
2. D 解析：单次 new Thread () 执行完后，线程会死亡，整个 ThreadLocalMap 会被回收，不会泄漏。
3. C 解析：TTL 专门解决线程池场景下的父子线程数据传递，是工业界标准方案。
4. C 解析：标准透传流程，入站拦截器负责接收，出站拦截器负责传递。

### 三、简答题

1. **内存泄漏原因**：
    
    - ThreadLocalMap 的 key 是弱引用，GC 会回收没有强引用的 key
    - Value 是强引用，只要线程存活，value 就不会被回收
    - 线程池的线程长期存活，会导致 value 永久泄漏
        
        **解决方法**：使用完 ThreadLocal 后，必须在 `finally` 块中手动调用 `remove ()` 方法。
    
2. **原因**：
    
    - 性能差：全局 ConcurrentHashMap 有锁竞争，ThreadLocal 无锁，性能高 10~100 倍
    - 不安全：全局 Map 任何人都能修改其他线程的数据，ThreadLocal 天然隔离
    - 泄漏更严重：全局 Map 生命周期和程序一样长，线程死亡后数据不会自动回收
    - 设计反了：用共享工具实现不共享的需求，违背设计初衷。
    
3. **失效原因**：
    
    InheritableThreadLocal 只在**创建新线程时**，复制父线程的 inheritableThreadLocals 数据。
    
    线程池是复用线程的，不是每次提交任务都创建新线程，所以后续提交的任务，会拿到线程第一次创建时复制的旧数据。
    
4. **原因**：
    
    - 代码冗余：如果每个接口都手动传 traceId、userId，会有大量重复代码
    - 易出错：容易漏传，导致链路断裂
    - 侵入性强：业务代码不需要关心这些公共数据，应该和业务逻辑解耦
    - 可维护性差：如果要新增一个透传字段，需要修改所有接口。
    

### 四、代码找错题

**bug 1**：TraceIdUtil 用了普通 ThreadLocal，异步线程拿不到主线程的 traceId

**修复**：替换为阿里 TransmittableThreadLocal：

Java

运行

```
private static final TransmittableThreadLocal<String> TRACE_ID = new TransmittableThreadLocal<>();
```

**bug 2**：WebTraceInterceptor 没有重写 afterCompletion 方法，没有清理 ThreadLocal，会导致内存泄漏

**修复**：添加 afterCompletion 方法：

Java

运行

```
@Override
Public void afterCompletion (HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
    TraceIdUtil.Remove ();
}
```

**bug 3**：原生线程池没有用 TTL 包装，即使换了 TTL，异步线程还是拿不到最新的 traceId

**修复**：用 TtlExecutors 包装线程池：

Java

运行

```
Private static final ExecutorService EXECUTOR = TtlExecutors.GetTtlExecutorService (
        Executors.NewFixedThreadPool (5)
);
```
