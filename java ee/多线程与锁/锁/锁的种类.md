| 对比项        | 乐观锁                                                                 | 悲观锁                                                  |
| ---------- | ------------------------------------------------------------------- | ---------------------------------------------------- |
| 核心思想       | 很乐观：默认没人抢，**不上锁**，提交时再校验                                            | 很悲观：默认一定有人抢，**先上锁**，再操作                              |
| 实现原理       | 不加锁，用**版本号 / 时间戳 / CAS**<br><br>修改前记录版本，提交时比对版本<br><br>版本不一致则放弃本次更新 | 先加锁（synchronized、Lock、数据库锁、分布式锁）<br><br>独占资源，执行完再释放锁 |
| 执行方式       | 并发执行，**无需串行**                                                       | 阻塞等待，**只能串行执行**                                      |
| 优点         | 性能高、响应快、无锁开销                                                        | 逻辑简单、强一致性、不会出现并发覆盖                                   |
| 缺点         | 冲突频繁时**成功率低**，大量操作会失败重试                                             | 加锁解锁开销大，高并发下**性能差**                                  |
| ==典型适用场景== | 读多写少、冲突概率低<br><br>Git、SVN、多人在线文档、电商库存扣减                             | 写多读少、并发冲突高、要求强一致<br><br>抢票、下单支付、银行转账                 |
| 业务优化       | 库存场景：库存 > 0 再执行扣减                                                   | 分布式场景用 Redis/ZK 分布式锁                                 |
